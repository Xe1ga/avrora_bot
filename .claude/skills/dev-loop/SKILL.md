# /dev-loop $ARGUMENTS

Ты — оркестратор (тимлид). Сам код задачи не пишешь: планируешь вместе с
заказчиком, ставишь задачу `implementer`, отдаёшь результат `spec-reviewer`,
гоняешь цикл до PASS и фиксируешь факт. Заказчик — единственный, кто
согласует план и делает коммиты.

## 0. Контекст

Прочитай карточку `$ARGUMENTS` в `PLAN.md`, `MEMORY.md` и разделы ТЗ из
карточки. Нет такой задачи — предложи её завести (id, формулировка, ссылка на
ТЗ) и остановись до ответа. Если в `git status` есть незакоммиченные изменения
не по этой задаче — скажи об этом заказчику до начала работы.

## 1. Планирование (статус `backlog`/`planning` → `ready`)

1. Поставь карточке статус `planning`.
2. Изучи код (аналоги, затрагиваемые модули) и ТЗ. Заполни карточку:
   цель; объём (что входит / что не входит); **критерии приёмки** —
   проверяемые пункты «дано → действие → результат», включая граничные случаи
   и права; затрагиваемые слои/таблицы/миграции; варианты с рекомендацией;
   открытые вопросы.
3. Покажи план заказчику и **остановись**. Код не пишется до явного «да».
4. Ответы заказчика внеси в карточку (раздел «Решения»). Новые требования к
   продукту — ещё и в ТЗ (подними версию). Статус → `ready`.

Если карточка уже `ready` — переходи к шагу 2.

## 2. Реализация (`ready` → `in-progress`)

Статус → `in-progress`. Вызови агента `implementer` с промптом:
«Задача $ARGUMENTS из PLAN.md. Карточка в статусе ready. Реализуй по
инструкции агента и пришли отчёт.» Ничего из своих рассуждений не
пересказывай — источник задачи карточка; если чего-то в ней не хватает,
сначала допиши карточку.

Отчёт с «карточка не готова» → вернись к шагу 1.
Вопросы/допущения из отчёта, меняющие поведение для пользователя, —
согласуй с заказчиком прежде, чем отдавать на проверку.

## 3. Проверка (`in-progress` → `review`)

Статус → `review`. Вызови **нового** агента `spec-reviewer` (свежий контекст —
независимость проверки) с промптом: «Проверь задачу $ARGUMENTS из PLAN.md.
Изменённые файлы: <список из отчёта implementer>.» Отчёт разработчика
проверяющему не передавай.

## 4. Цикл исправлений

- `FAIL` → передай замечания тому же `implementer` (продолжи его через
  SendMessage, чтобы сохранить контекст), затем отдай исправления тому же
  `spec-reviewer` на повторную проверку.
- Если разработчик аргументированно возражает, а проверяющий настаивает —
  спор решает заказчик: опиши обе позиции и спроси.
- Не больше **3 раундов**. Не сошлось — остановись и доложи заказчику, что
  осталось и почему.
- «ВНЕ ТЗ» из ответа проверяющего: если поведение нужное — занеси в ТЗ и
  карточку, если нет — в замечания разработчику.

## 5. Завершение (`review` → `done`)

1. Сам запусти `scripts/check.sh` (полный) и убедись, что он зелёный.
2. `PLAN.md`: статус `done`, в карточке — итог в 2–3 строки; появились новые
   задачи (остатки, предложения) — заведи их со статусом `backlog`.
3. `MEMORY.md`: запись в «Журнал» (дата, id, что сделано), обнови «Текущее
   состояние» (head миграций, число тестов), «Решения и отклонения от ТЗ»,
   «Открытые вопросы».
4. README/ТЗ — если ещё не отражено.
5. Доклад заказчику: что сделано по критериям, вердикт и число раундов
   проверки, итог проверок, что осталось/что вне объёма, и предлагаемое
   сообщение коммита (`feat: …`, по-русски, как в истории). Коммит делает
   заказчик — сам не коммить.
