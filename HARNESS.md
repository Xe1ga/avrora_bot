# HARNESS — агентский цикл разработки avrora_bot

Как мы ведём задачи с Claude Code: кто что делает, где что лежит и как
запустить цикл.

## Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| Заказчик | вы | ставит задачи, согласует план, решает спорное, коммитит | — |
| Оркестратор | основная сессия Claude (`/dev-loop`) | планирует с вами, ведёт `PLAN.md` / `MEMORY.md` / ТЗ, раздаёт работу агентам, гоняет цикл до PASS | не пишет код задачи |
| implementer | агент `.claude/agents/implementer.md` | пишет код, тесты, миграции, README по карточке | не трогает план/факт/ТЗ, не коммитит |
| spec-reviewer | агент `.claude/agents/spec-reviewer.md` | независимо сверяет результат с ТЗ и критериями приёмки, гоняет проверки, выносит PASS/FAIL | не меняет код |

Почему так: проверяющий работает в свежем контексте и не видит рассуждений
разработчика — он проверяет то, что получилось, а не то, что задумывалось.
Источник задачи для обоих — карточка в `PLAN.md`, поэтому качество карточки
(критерии приёмки) определяет качество результата.

## Артефакты

| Файл | Назначение |
|---|---|
| `Техническое задание на разработку.md` | требования; новые требования вносятся сюда с поднятием версии |
| `PLAN.md` | бэклог: все задачи ТЗ + новые, статусы, карточки с критериями приёмки |
| `MEMORY.md` | факт: журнал сделанного, решения, отклонения от ТЗ, окружение |
| `CLAUDE.md` | правила для Claude (читается автоматически в каждой сессии) |
| `.claude/skills/dev-loop/SKILL.md` | сценарий оркестратора — команда `/dev-loop` |
| `.claude/agents/*.md` | инструкции агентов |
| `scripts/check.sh` | единая проверка качества (quality gate) |

## Цикл задачи

```
 backlog ──► planning ──► ready ──► in-progress ──► review ──► done
             │  ▲          (ваше      implementer    spec-reviewer   │
             │  └ вопросы   «да»)          ▲              │          │
             ▼    к вам                    └── FAIL ◄─────┘          ▼
        карточка: цель, объём,          (≤ 3 раундов, дальше     MEMORY.md,
        критерии приёмки, решения        решаете вы)             коммит — вы
```

1. **Планирование.** Оркестратор изучает ТЗ и код, заполняет карточку
   (цель, что входит/не входит, критерии приёмки, варианты, вопросы) и
   останавливается. Вы отвечаете на вопросы и говорите «да» — статус `ready`.
2. **Реализация.** implementer пишет код и тесты, прогоняет
   `scripts/check.sh` на своих тестах, присылает отчёт по критериям.
3. **Проверка.** spec-reviewer сверяет с ТЗ и карточкой, запускает полный
   `scripts/check.sh`, отвечает `PASS` или `FAIL` со списком замечаний
   (каждое — со ссылкой на ТЗ/карточку и конкретным сценарием).
4. **Исправления.** При FAIL замечания уходят разработчику, затем снова на
   проверку. Не больше 3 раундов; спор «разработчик против проверяющего»
   решаете вы.
5. **Завершение.** Оркестратор прогоняет финальную проверку, ставит `done`
   в `PLAN.md`, пишет факт в `MEMORY.md` и предлагает сообщение коммита.
   Коммитите вы.

## Как пользоваться

Запуск Claude Code — из папки проекта (`avrora_bot`), чтобы подхватились
`CLAUDE.md`, агенты и команда.

- **Взять задачу:** `/dev-loop T-3.1` — начнётся планирование; дальше
  отвечаете на вопросы и даёте «да».
- **Продолжить согласованную задачу:** тот же `/dev-loop T-3.1` — если
  карточка `ready`, цикл сразу идёт в реализацию.
- **Новая задача или требование:** просто напишите её словами — Claude
  заведёт карточку в `PLAN.md` (и требование в ТЗ), затем `/dev-loop <id>`.
- **Что дальше / где мы:** спросите «что дальше по плану?» — ответ строится по
  `PLAN.md` и `MEMORY.md`.
- **Проверить руками:** `scripts/check.sh` (всё) или
  `scripts/check.sh tests/test_birthdays_flow.py` (выборочно);
  `scripts/check.sh --no-tests` — только линтер и миграции.
- **Посмотреть агентов:** `/agents`.
- **Мелкая правка без цикла** (опечатка в тексте, README) — просто попросите;
  цикл нужен для задач из `PLAN.md`.

Пока агенты работают, оркестратор пишет короткие статусы: «implementer
закончил, отдаю на проверку», «FAIL: 2 замечания, раунд 2».

## Что можно добавить позже

- **Хук на форматирование** (`PostToolUse` → `ruff format` изменённого файла),
  чтобы implementer не тратил раунды на стиль.
- **Отдельный агент-тестировщик**, который пишет приёмочные тесты по
  критериям карточки до реализации (TDD-вариант цикла).
- **Изоляция в git worktree** для параллельных задач — на WSL-маунте git
  работает с ограничениями, поэтому пока задачи идут последовательно в
  основной папке.
- **CI на GitHub Actions** с тем же `scripts/check.sh` — проверка каждого push.
