# avrora_bot

Чат-бот VK для автоматизации управления волейбольным клубом «Аврора» (г. Вологда).

Реализован **Этап 1 (MVP)** согласно «Техническое задание на разработку.md»:
регистрация и ролевая модель, учёт абонементов (голосование → расчёт →
фиксация оплат → отчёт), разовые посещения с редактируемым тарифом, календарь
тренировок/игр, журнал административных действий.

## Технологии

Python 3.14 · vkbottle (Long Poll) · SQLAlchemy 2.0 (async) + Alembic ·
PostgreSQL 16 · openpyxl · structlog · Docker Compose. Управление зависимостями — `uv`.

## Архитектура

Гексагональная (ports & adapters):

```
src/avrora_bot/
  domain/        — сущности, доменные сервисы (расчёт стоимости месяца
                   и суммы абонемента), порты (Protocol-интерфейсы)
  application/   — use case'ы и сервисы (permissions, action_log)
  adapters/
    database/    — ORM-модели, репозитории, Unit of Work, Alembic, сидинг
    vk/          — бот vkbottle, хендлеры, FSM, клавиатуры, middleware
    reports/     — генерация XLSX
    legal/       — чтение версий документов о ПД из docs/legal/*.html
  composition.py — сборка зависимостей (composition root)
  app.py         — инициализация и запуск
```

## Быстрый старт (Docker)

1. Скопируйте шаблон окружения и заполните значения:

   ```sh
   cp .env.example .env
   # отредактируйте .env: VK_TOKEN, VK_GROUP_ID, POSTGRES_PASSWORD,
   # BOOTSTRAP_ADMIN_VK_ID (ваш личный vk_id — станет администратором)
   ```

2. Запустите:

   ```sh
   docker compose up -d --build
   ```

   Контейнер дождётся PostgreSQL, применит миграции Alembic и запустит бота.

3. Напишите сообществу в VK «начать» — бот ответит меню.

## Как получить VK-токен

Сообщество → **Управление → Настройки → Работа с API**:
- **Ключи доступа** → создать ключ с правами «Сообщения сообщества» и
  «Управление сообществом» → это `VK_TOKEN`.
- **Long Poll API** → включить, версия API 5.199, событие «Входящее сообщение».
- **Сообщения** → включить сообщения сообщества.

```sh

```

Бот уже в проде: любое изменение схемы — только **новой ревизией Alembic
поверх head**; применённые ревизии (включая `initial_schema`) не
редактируются и не схлопываются. Миграции не импортируют код проекта.

## Команды бота (Этап 1)

Игрок: `начать`, `помощь`, `регистрация`, `мой статус`, `календарь [YYYY-MM]`.

Сборщик платежей:
- `расчёт YYYY-MM <кол-во>` — предварительный расчёт суммы абонемента;
- `голоса YYYY-MM` + список vk_id (с новых строк) — зафиксировать голосование;
- `сумма YYYY-MM <значение>` — переопределить сумму на человека;
- `оплатил YYYY-MM <vk_id>` / `не оплатил YYYY-MM <vk_id>`;
- `сводка YYYY-MM` — краткий отчёт; `xlsx YYYY-MM` — полный отчёт файлом;
- `разовый тариф <сумма>`, `посетили [ДД.ММ.ГГГГ]`, `разовое оплатил <vk_id|ФИО>`,
  `разовые YYYY-MM`; `посетили` и `разовое оплатил` есть и кнопками в разделе
  «🎫 Разовые»: «🎫 Посетили» (спросит дату, есть «Сегодня») и «💵 Оплатил»
  (спросит участника);
- `разовые отчёт YYYY-MM` — отчёт по разовым посещениям файлом XLSX (та же
  кнопка «📊 Отчёт xlsx» в разделе «🎫 Разовые»); форма повторяет ручную
  таблицу клуба: дата тренировки, ФИО, сумма, казначей, примечание;
- `редактировать оплату <id>` — правка разового посещения кнопками, включая
  примечание (`-` очищает).

Куратор (кнопки раздела «🗓 Календарь: управление»): «➕ Добавить событие»
(спросит дату, тип, время, место), «🗑 Удалить событие» и «❌ Отменить
событие» (спросят id), «📅 Создать тренировки на следующий месяц». См.
«Календарь» ниже.

Администратор: `заявки`, кнопки подтверждения/отклонения,
`добавить <vk_id> <роль> <ФИО>`, `роль <vk_id> <роль>`, `снять роль <vk_id> <роль>`,
`удалить пользователя <vk_id>` — уничтожение персональных данных по отзыву
согласия (см. ниже).

## Календарь

События (`calendar_events`) — тренировки и игры: дата, время, тип, место,
комментарий и статус.

**Статусы:**

| Статус | Когда ставится |
|---|---|
| `planned` — запланировано | автоматически при создании (кнопкой или генератором) |
| `done` — выполнено | автоматически, когда время события вышло (см. ниже) |
| `cancelled` — отмена | вручную куратором: «❌ Отменить событие» + id |

Удаление (`🗑`) — для ошибочных записей; отмена оставляет событие в истории
и на странице расписания. Отменить можно только запланированное событие.

**Автозавершение.** Бот при старте и затем каждые 15 минут переводит в
`done` запланированные события, которые уже закончились (время — по `TZ`):
тренировка из недельного шаблона — по концу своего слота
`schedule_template`, другие события со временем — через 2 часа после
начала, событие без времени — в конце дня.

**Что видно в чате** (`календарь`, `календарь YYYY-MM`): за текущий и
будущие месяцы — только запланированные события, за прошедшие месяцы —
только выполненные (история). Отменённые в чат не попадают; статус в
тексте не обозначается. Куратор и администратор видят у каждого события
`[id N]` — его вводят в «Удалить/Отменить событие».

**Генерация тренировок.** «📅 Создать тренировки на следующий месяц»
создаёт тренировки по активным слотам `schedule_template` и подставляет
место/тренера по умолчанию из `schedule_template.place`. Уже существующие
(тот же день и время, в т. ч. отменённые) не создаются повторно.

**Страница расписания** `docs/schedule.html` (GitHub Pages, ссылка
`SCHEDULE_URL` в конце сообщения «Календарь») собирается вручную:

```sh
uv run python scripts/build_schedule_page.py            # текущий + следующий месяц
uv run python scripts/build_schedule_page.py --months 2026-09 2026-11
git add docs/schedule.html && git commit && git push
```

На странице показаны все статусы: выполненные — с «✓», отменённые —
зачёркнуты с пометкой «отмена» (есть фильтр «Скрыть отменённые»). Перед
сборкой скрипт сам доводит статусы до актуальных, как фоновая задача бота.

## Документы о персональных данных (152-ФЗ)

Тексты лежат в репозитории и публикуются как статические страницы
(GitHub Pages): `docs/legal/consent.html` — согласие на обработку ПД,
`docs/legal/privacy-policy.html` — политика обработки ПД.

Версия документа берётся из заголовка самой страницы — строки вида
`<div class="version">Версия 1.0 от 14 сентября 2026 г.</div>`. При старте
бот читает оба файла (каталог задаётся `LEGAL_DOCS_DIR`, по умолчанию
`docs/legal`) и регистрирует ещё не известные версии в таблице
`legal_documents`: версия, дата, ссылка на публикацию, sha256 и полный
HTML на момент регистрации.

Журнал согласий `user_consents` ссылается на конкретные строки
`legal_documents` (согласие + политика), поэтому по каждому пользователю
всегда восстановим точный текст, который ему показали и который он принял,
даже если файл в репозитории потом переписали.

Публикация новой редакции:

1. Поправить текст в `docs/legal/*.html` и **поднять номер версии** в
   заголовке страницы.
2. Задеплоить (`docker compose up -d --build`) — новая версия
   зарегистрируется при старте сама; старые строки остаются нетронутыми.

Правка текста без нового номера версии в БД не попадёт: при старте в лог
пишется предупреждение `seed.legal_document.changed_without_new_version`, а
пользователи продолжат соглашаться с ранее зафиксированным текстом.

## Удаление персональных данных (отзыв согласия, 152-ФЗ ст. 21)

По запросу на отзыв согласия (пользователь пишет в личные сообщения
группы — порядок описан в `docs/legal/consent.html`, п. 7) администратор
выполняет команду `удалить пользователя <vk_id>`. Бот показывает ФИО и
роли пользователя и требует явного текстового подтверждения
(`ПОДТВЕРЖДАЮ`) — действие необратимо.

Что происходит (`UserManagementUseCases.delete_personal_data`):

- **уничтожается:** ФИО (шифрованное значение перезаписывается меткой,
  восстановить исходное невозможно), телефон, дата рождения, рост; все
  роли снимаются; статус профиля становится `deleted`.
- **не трогается:** `vk_id` (это открытая информация самого профиля VK,
  не тайна, которую хранит бот, — без него профиль было бы невозможно
  однозначно узнать при повторном обращении); история оплат/посещений
  (`subscription_payments`, `one_time_payments` — это факты «оплатил/не
  оплатил», не персональные данные, нужны для отчётности за прошлые
  месяцы); запись в `user_consents` (доказательство того, что согласие
  было получено правомерно и когда именно отозвано — нужна оператору для
  защиты при проверке регулятора).

Если тот же vk_id позже напишет `регистрация` заново — это не считается
дублем: та же строка `users` переиспользуется, данные и согласие
записываются заново, статус возвращается в `pending`.
