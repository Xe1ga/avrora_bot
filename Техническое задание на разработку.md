# Техническое задание
## Чат-бот для автоматизации управления волейбольным клубом ВК «Аврора» (г. Вологда)

**Версия документа:** 1.0
**Дата:** 31.08.2026
**Платформа:** VK (сообщество [vk.ru/avrora_volley](https://vk.ru/avrora_volley))

---

## 0. Глоссарий и соответствие терминов

В тексте ТЗ используются термины, привычные для проектной команды клуба. Ниже — их соответствие терминологии, принятой на архитектурных комитетах при разработке ПО.

| Термин в задаче                  | Архитектурный термин                        | Пояснение |
|-----------------------------------|----------------------------------------------|-----------|
| Ответственный исполнитель         | Роль **Cборщик платежей** (`collector`)      | Пользователь с правом фиксировать оплаты и вести сбор |
| Ответственное лицо (ДР/календарь) | Роль **Куратор** (`curator`)                  | Пользователь с правом редактировать календарь и/или получать уведомления о ДР |
| Абонемент                         | **Подписка на период** (`subscription`)       | Сущность с привязкой к месяцу и сумме |
| Опрос ВК                          | **Внешний источник голосования** (`vk_poll`)  | Источник данных, синхронизируемый вручную/автоматически |
| Разовое посещение                 | **Разовый платёж** (`one_time_payment`)       | Платёж вне подписки, с изменяемым тарифом |

---

## 1. Цели и назначение системы

**Цель:** автоматизировать организационные и финансовые процессы волейбольного клуба «Аврора», снизив ручную нагрузку на администраторов сообщества VK.

**Назначение системы:**
- единая точка входа — чат-бот в VK;
- учёт оплаты абонементов и разовых посещений;
- администрирование группы (публикация постов);
- напоминания о днях рождения;
- учёт сборов на подарки;
- ведение календаря тренировок и игр.

---

## 2. Роли и права доступа

| Роль          | Кто назначает         | Права |
|---------------|------------------------|-------|
| **Администратор** | Назначается вручную (соответствует администратору сообщества VK) | Полный доступ ко всем функциям бота; управление ролями; публикация постов от имени сообщества |
| **Сборщик платежей** (`collector`) | Администратор | Ввод списка проголосовавших за абонемент; фиксация оплат; создание сборов на подарки; редактирование текущего тарифа разового посещения |
| **Куратор** (`curator`) | Администратор | Получение уведомлений о днях рождения; редактирование календаря на месяц |
| **Игрок** (`player`) | Самостоятельная регистрация через бота с подтверждением администратором, либо добавление/приглашение администратором вручную | Просмотр своего статуса оплаты, календаря, участие в сборах |

Права проверяются перед каждым действием на основании роли, привязанной к `vk_user_id`. Действия администраторов и сборщиков логируются (см. раздел 6.3).

## 3. Функциональные требования

### 3.1 Администрирование группы VK

- Публикация постов от имени сообщества доступна **только** пользователям с ролью «Администратор».
- Бот проверяет право на публикацию через VK API (`groups.getMembers` с фильтром по администраторам) перед выполнением действия — право не хранится статично, а верифицируется.
- Поддержка отложенной публикации (черновик → подтверждение → публикация).

### 3.2 Учёт оплаты абонементов

Логика соответствует файлу «Оплата абонементов.md»:

1. **Голосование за абонемент на месяц.**
   - Основной сценарий: сборщик платежей вручную вносит в бота список проголосовавших (ФИО/vk_id) через диалоговую команду.
   - Дополнительный сценарий: бот может по команде сборщика запросить и прочитать результаты нативного опроса VK (`polls.getVotes`) как вспомогательный источник — сборщик сверяет и подтверждает список перед сохранением. Ручной ввод имеет приоритет и является финальным источником истины.
2. **Расчёт суммы подписки.** Бот хранит месячный тариф (сумма сбора зала + тренера, см. 3.2.1) и автоматически делит его на число проголосовавших, округляя до рубля в большую сторону. Результат виден администратору/сборщику до фиксации.
3. **Фиксация оплат.** Для каждого участника, проголосовавшего за подписку, создаётся запись `subscription_payment` со статусом `оплачено` / `не оплачено`. Сборщик отмечает оплату вручную по факту перевода на карту (интеграция с реальными платёжными API — **вне периметра MVP**, см. раздел 3.2.2).
4. **Разовые посещения.** Тариф разового посещения — редактируемое администратором/сборщиком значение на текущий месяц (не жёстко зашито в код). Бот хранит историю изменений тарифа по месяцам.
5. **История и отчётность.** Бот формирует отчёт по месяцу: кто оплатил, кто нет, сумма собранных средств, сумма к переводу тренеру и за зал.
6. **Формат отчётов.**
   - *Краткая сводка* — текстовое сообщение в чате (список участников со статусом ✅/❌ и итоговыми суммами) для быстрого просмотра.
   - *Полный отчёт* — XLSX-файл, формируется по команде и отправляется как документ (`docs.getMessagesUploadServer` → `messages.send` с вложением). Используется для отчёта за месяц или за произвольный период (сентябрь 2026 — май 2027).
   - Рендер таблицы в виде изображения не используется (хуже читается, данные нельзя скопировать).

#### 3.2.1 Модель тарифов

- Стоимость зала (₽/час) и стоимость тренировки с тренером (₽/тренировка) — редактируемые параметры, хранятся в таблице `tariffs` с датой начала действия.
- Расписание тренировок (день недели, диапазон времени) хранится в таблице `schedule_template` и используется для автоматического расчёта часов зала и числа тренировок в месяце (аналогично таблице «По месяцам» из исходного документа).

#### 3.2.2 Границы MVP по оплате

- **В MVP:** только фиксация факта оплаты сборщиком вручную (перевод по-прежнему происходит на карту вне бота).
- **Вне MVP (задел на будущее):** интеграция с API банка/СБП для автоматического подтверждения поступления средств — закладывается как отдельный модуль, не блокирующий MVP.

### 3.3 Публикация постов в стиле клуба

- Бот хранит образцы ранее опубликованных постов (или обращается к ним через `wall.get`) для использования в качестве стилевого ориентира при формировании текста нового поста (ручной ввод администратором с помощью бота как редактора/помощника, либо генерация черновика с последующим подтверждением).
- Публикация — только после явного подтверждения администратором.

### 3.4 Учёт дней рождения

- Хранение дат рождения игроков и тренеров (вносится администратором или самим игроком через бота).
- Ежедневная фоновая задача проверяет предстоящие дни рождения (например, за 3 дня и в день ДР).
- Уведомления отправляются **только** пользователям с ролью «Куратор», явно назначенным администратором.

### 3.5 Сборы на подарки

- Отдельная от подписок сущность `gift_collection`: название сбора, список участников (ФИО), внесённая сумма, статус (`собрано` / `в процессе`).
- Ведётся сборщиком платежей; отчёт по сбору доступен администратору и куратору.

### 3.6 Регистрация пользователей

- **Самостоятельная регистрация.** Игрок пишет боту (обязательное условие VK API — бот не может писать первым пользователю, который не начал диалог), заполняет ФИО и дату рождения. Заявка попадает в очередь на подтверждение.
- **Подтверждение администратором.** Администратор видит список заявок в боте и подтверждает/отклоняет их. До подтверждения пользователь имеет статус `pending` и не получает игровых прав.
- **Добавление администратором вручную.** Администратор может сразу создать профиль пользователя по его `vk_id` (например, полученному из пересланного сообщения или ссылки на профиль), минуя этап заявки. Профиль получает статус `pending`, роль назначается сразу — при этом функции, требующие взаимодействия бота с пользователем (уведомления, личные команды), станут доступны только после того, как сам пользователь напишет боту хотя бы одно сообщение (техническое ограничение VK: бот не может инициировать переписку без встречного действия пользователя).
- **Приглашение.** Для ускорения первого контакта администратор может отправить пользователю прямую ссылку вида `vk.me/<id_сообщества>` — переход по ней открывает диалог с ботом.

### 3.7 Календарь тренировок и игр

- Хранение календарного плана на месяц: дата, время, тип события (тренировка/игра), место, комментарий.
- Редактирование — только пользователями с ролью «Куратор», назначенными администратором.
- Просмотр календаря доступен всем игрокам через команду бота.

## 4. Архитектура решения

### 4.1 Технологический стек

| Компонент | Выбор |
|---|---|
| Язык | Python 3.12+ |
| VK Bots API framework | **vkbottle** (async) |
| База данных | **PostgreSQL 16** |
| ORM / миграции | SQLAlchemy 2.0 (async) + Alembic |
| Планировщик фоновых задач | APScheduler (для уведомлений о ДР и ежемесячных операций) |
| Формирование отчётов | openpyxl (генерация XLSX-отчётов) |
| Контейнеризация | Docker + Docker Compose |
| Хранение секретов | Переменные окружения (`.env`, не в репозитории) / Docker secrets |
| Логирование | structlog / стандартный `logging` с ротацией файлов |

### 4.2 Компонентная схема

```
┌─────────────────┐      ┌──────────────────┐      ┌──────────────┐
│   VK Bots API    │◄────►│   Bot-сервис      │◄────►│  PostgreSQL   │
│ (Callback API /  │      │  (vkbottle,       │      │               │
│  Long Poll)       │      │  Docker-контейнер)│      └──────────────┘
└─────────────────┘      └────────┬─────────┘
                                    │
                          ┌────────▼─────────┐
                          │  Планировщик      │
                          │  (APScheduler):   │
                          │  - ДР             │
                          │  - месячный отчёт │
                          └───────────────────┘
```

### 4.3 Модель данных (основные сущности)

- `users` — vk_id, ФИО, дата рождения, роль(и)
- `roles` — справочник ролей (`admin`, `collector`, `curator`, `player`)
- `user_roles` — связь пользователь ↔ роль (многие ко многим, с датой назначения)
- `tariffs` — тариф зала/тренера/разового посещения, дата начала действия
- `schedule_template` — шаблон недельного расписания тренировок
- `subscriptions` — подписка на месяц: месяц, итоговая сумма, число участников, сумма на человека
- `subscription_payments` — участник подписки: статус оплаты, дата отметки, кто отметил
- `one_time_payments` — разовые посещения: участник, дата, сумма, статус
- `gift_collections` / `gift_collection_entries` — сборы на подарки и их участники
- `calendar_events` — тренировки/игры: дата, время, тип, место, комментарий, автор
- `posts_log` — журнал опубликованных постов (для стилевого анализа и аудита)
- `action_log` — журнал действий администраторов/сборщиков/кураторов

## 5. Технические требования к безопасности

1. Токен сообщества VK и параметры подключения к БД хранятся исключительно в переменных окружения, не коммитятся в репозиторий.
2. Все действия, изменяющие данные (публикация поста, фиксация оплаты, редактирование календаря), проходят проверку роли **на момент выполнения** — не полагаться на закэшированные права.
3. Использование `Callback API` с проверкой `confirmation`-токена и `secret key` для валидации запросов от VK.
4. Ограничение частоты команд (rate limiting) для защиты от спама/флуда со стороны пользователей.
5. Логирование всех административных действий (`action_log`) с указанием vk_id инициатора и временной метки.
6. Регулярное резервное копирование базы данных (см. раздел 7).

## 6. Этапы реализации (Roadmap)

### Этап 1 — MVP (базовый функционал)
- Регистрация пользователей и ролевая модель.
- Учёт оплаты абонементов: ручной ввод голосования, расчёт суммы, фиксация оплат, отчёт по месяцу.
- Разовые посещения с редактируемым тарифом.
- Календарь тренировок/игр (просмотр всеми, редактирование куратором).
- Базовое логирование действий.

### Этап 2 — Коммуникации
- Публикация постов от имени сообщества (с подтверждением администратором).
- Уведомления о днях рождения кураторам.
- Чтение результатов опроса VK как вспомогательного источника при голосовании за абонемент.

### Этап 3 — Финансовый учёт сборов
- Сборы на подарки (создание, учёт участников, отчётность).
- Расширенная отчётность по всем видам платежей (экспорт, история за период сентябрь 2026 — май 2027).

### Этап 4 — Задел на будущее (вне текущего периметра)
- Интеграция с реальными платёжными API (СБП/банк) для автоматического подтверждения оплат.
- Генерация черновиков постов в стиле клуба с помощью LLM.

---

## 7. Нефункциональные требования

- **Надёжность:** бот должен восстанавливать соединение с VK Long Poll/Callback API после сбоя без потери событий.
- **Резервное копирование:** ежедневный дамп PostgreSQL с хранением не менее 30 дней.
- **Масштабируемость:** архитектура рассчитана на клуб текущего размера (~30 человек), но модель данных допускает рост числа участников и групп/секций без переработки схемы.
- **Наблюдаемость:** структурированные логи, доступные для просмотра администратором (файл или консоль контейнера).
- **Разворачивание:** воспроизводимая сборка через `docker-compose up` на VPS, конфигурация через `.env`.

## 8. Зафиксированные решения по открытым вопросам

- **Отчёты:** краткая сводка текстом в чате + полный отчёт в XLSX по запросу (см. раздел 3.2, п.6).
- **Регистрация:** самостоятельная регистрация с подтверждением администратором, либо ручное добавление/приглашение администратором (см. раздел 3.6).
- **Многоязычность:** не требуется, интерфейс только на русском языке.
